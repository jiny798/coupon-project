# 부하 테스트 결과

## 구성

```
k6 서버 ── 사설 IP :8080 ──▶ 앱 서버 (t3.medium · vCPU 2 · 4GiB)
                              api · consumer · MySQL · Redis · Kafka · Prometheus · Grafana (컨테이너 11개)
```

- AWS 서울, t3.medium 2대 (같은 서브넷), Rate Limiter 없음
- 발급: Redis 판정(SADD · INCR) → Kafka 발행(ack 대기) → 202, DB 저장은 컨슈머(스레드 3)

## 1. VU 500 → 1,000 (OSIV 켜짐)

| | VU 500 (1-1) | VU 1,000 (1-2) |
|---|---|---|
| 조건 | 0→100→400→500, 12분, 재고 10만 | 0→100→400→700→1,000, 15분, 재고 60만 |
| 한 줄 | 여유 있음 | API가 초당 약 680건에서 막힘 |
| 요청 / 실패 | 248,733 / 0 | 421,201 / 0 |
| p95 (k6) | 55ms | 1.03s |
| API TPS | 평균 345, 발급 경로 최대 약 415/s | 평균 465, 650~680/s에서 평평 (최대 709) |
| 컨슈머 처리 | 최대 258/s (약 250에서 평평) | 최대 254/s → VU 700 이후 약 210/s |
| Lag 최대 | 28K (매진 후 약 2분 뒤 0) | 247K (부하 끝나고 약 14분 뒤 0) |
| 앱 서버 CPU | 최고 76% | 96% |
| 막힌 곳 | 컨슈머 (스레드 3 × 건당 약 12ms) | API DB 커넥션 10/10 · 대기 약 190, 서버 CPU |
| 정합성 | DB = Redis = 100,000 | DB = Redis = 421,201 |

- VU 500은 재고 10만이 중간에 소진돼서, 500 VU 구간은 매진 응답이었다 (API 최대 496/s는 매진 응답 값).
- VU 1,000은 15분 내내 발급되도록 재고를 60만으로 늘렸다.

## 2. 문제: API가 DB 커넥션을 쥐고 있다

| VU 700 ~ 1,000 구간 | 값 |
|---|---|
| 톰캣 스레드 | 200 / 200 |
| DB 커넥션 (API) | 사용 중 10 / 10, 대기 약 190 |
| MySQL 실행 중 쿼리 | 4 ~ 7 (DB는 바쁘지 않음) |

- 커넥션 10개로 초당 약 670건 → 요청 하나가 커넥션을 약 15ms씩 쥔 셈 (계산). 쿠폰 조회 한 번은 1ms 안팎.
- 원인: OSIV(`open-in-view`) 기본값이 켜짐 → 쿠폰 조회 때 빌린 커넥션을 요청이 끝날 때까지 쥔다.

```
OSIV 켜짐   조회 ─ 커넥션 ═══════════════════════════ 요청 끝에 반납
                    Redis · Kafka ack 대기 동안에도 쥠
OSIV 꺼짐   조회 ─ 커넥션 ═ 반납
```
