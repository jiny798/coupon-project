# 부하 테스트 결과

## 목표

가장 몰릴 때 1초에 5,000명이 쿠폰을 누르고, 그 상태가 5분 동안 이어진다. 앞뒤로 천천히 늘고 주는 시간까지 합치면 17분 동안 약 280만 명이다(재고 300만이라 모두 발급되는, 저장 쪽에 가장 힘든 경우). 이때

| # | 항목 | 목표 | 어디서 재나 |
|---|---|---|---|
| 1 | 응답 시간 | p90 1초, p95 2초 이내 | k6 |
| 2 | 실패 | 0건 | k6 `http_req_failed` |
| 3 | 받아 낸 양 | 1초 5,000명 구간에서 초당 4,750건 이상 | API TPS |
| 4 | DB 저장까지 | 발급 응답 뒤 가장 늦은 것도 60초 이내 | Lag 최대 ÷ 컨슈머 처리량 |
| 5 | 정합성 | 발급 수량 = Redis 셋 = Redis 순번 = DB = k6 요청 수 | 끝난 뒤 확인 |
| 6 | 서버 여유 | 가장 바쁜 서버도 CPU 80% 이하 | CloudWatch |
| 7 | 측정 신뢰 | k6 서버 CPU 80% 이하 | vmstat · CloudWatch |

- 응답 목표는 큰 이벤트라 1~2초는 기다릴 수 있다고 보고 잡았다. 대신 k6는 서버가 느리면 덜 보내서 응답이 어느 선에서 멈춘 것처럼 보이는데, 실제로는 사람이 계속 오니 처리량이 도착량보다 작으면 줄이 끝없이 늘어난다. 그래서 받아 낸 양(3)을 같이 본다.
- DB 저장 60초는 발급 응답을 받고 쿠폰함을 열었을 때 1분 안에는 보여야 한다고 보고 잡았다. 5분 동안 초당 약 4,850건이 들어올 때 이걸 지키려면 컨슈머가 초당 약 4,040건 이상 저장해야 한다.
- 실제 오픈은 정각에 훨씬 뾰족하게 몰리고 재고가 작아 금방 매진된다. 여기 목표는 오래, 꾸준히, 전부 저장까지 가는 경우 기준이다.

## 환경

- AWS 서울 리전, t3.medium 2대 (같은 서브넷)
- 앱 서버 1대에 api, consumer, MySQL, Redis, Kafka, Prometheus, Grafana를 전부 컨테이너로 올림
- k6 서버에서 앱 서버 사설 IP로 부하를 줌
- Rate Limiter 없음

발급 흐름은 Redis로 중복이랑 순번을 판정하고, Kafka에 발행해서 ack를 받으면 202를 준다. DB 저장은 컨슈머가 따로 한다.

통과 기준은 k6 threshold 그대로 성공 응답 99% 이상, p95 10초 이하.

## API DB 커넥션 대기

VU 1,000에서 VU 700을 넘어가면서 이렇게 됐다.

| 항목 | 값 |
|---|---|
| 톰캣 스레드 | 200 / 200 |
| API DB 커넥션 | 10 / 10 사용, 약 190 대기 |
| MySQL 실행 중 쿼리 | 4~7개 |

MySQL에서 한 번에 처리 중인 쿼리는 4~7개뿐이라 DB가 밀린 건 아니었는데 커넥션이 모자랐다. 커넥션 10개로 초당 670건 정도를 처리했으니 요청 하나가 커넥션을 15ms쯤 잡고 있었던 셈이다. 쿠폰 조회 한 번은 1ms도 안 걸린다.

원인은 OSIV(open-in-view)로 봤다. 기본값이 켜져 있어서 쿠폰 조회 때 가져간 커넥션을 요청이 끝날 때까지 들고 있는다. 그 사이에 Redis 호출이랑 Kafka ack 기다리는 시간도 다 들어간다.

```
OSIV 켜짐   조회 ── 커넥션 ═════════════════════════ 요청 끝날 때 반납
                     (Redis, Kafka ack 기다리는 동안에도 들고 있음)
OSIV 꺼짐   조회 ── 커넥션 ═ 바로 반납
```

VU 500 때도 같은 상황이었다. 매진 직전에 발급이 초당 415건 정도일 때 커넥션 대기가 잠깐 190 가까이 올라갔다.
그런데 매진 뒤에는 매진 응답을 초당 490건 정도로 더 많이 처리했는데도 대기가 없었다. 매진 응답은 Kafka를 안 거치니까, Kafka ack를 기다리는 동안 커넥션을 들고 있는 게 큰 것 같다.

응답이 빨라진 만큼 k6가 같은 15분 동안 9만 건 가까이 더 보냈다 (한 바퀴 평균 1.29초 → 1.07초).

API가 더 많이 받은 만큼 Kafka에도 더 많이 쌓였다. 컨슈머는 부하 중에 초당 210건 정도로 그대로라 Lag가 32만까지 갔고, 부하가 끝나 CPU가 풀리자 초당 320건 정도로 빨라졌다.

## 서버 분리

VU를 1,000으로 올리니 앱 서버 CPU가 95% 넘게 차면서 API 응답이 늦어졌고(p95 315ms), 같은 서버의 컨슈머도 느려져서 Lag가 32만까지 쌓였다. API, 컨슈머, DB, Kafka가 한 서버에서 CPU를 나눠 쓰는 게 원인으로 보여서 서버를 나눠 보려고 한다.

```
k6 ──8080──▶ API ──3306 · 6379 · 9092──▶ 인프라 (MySQL · Redis · Kafka)
                                           ▲
                          컨슈머 ──────────┘
모니터링 (Prometheus · Grafana) ── API · 컨슈머 · 인프라 수집
```

- t3.medium 4대 (API, 인프라, 컨슈머, k6) + t3.small 1대 (모니터링), 같은 서브넷
- MySQL · Kafka · JVM 메모리 설정은 한 대일 때와 같게 두고 서버만 나눴다
- OSIV 꺼짐, Rate Limiter 없음

컨슈머는 서버를 따로 줬는데도 초당 270건 정도에서 더 안 올라갔다. 컨슈머 서버 CPU는 13%뿐이었다. 스레드 3개가 한 건에 11ms 정도씩 쓰니까 3 ÷ 0.011 ≈ 270이 그대로 한계다. API가 초당 990건을 넣는 동안 Lag가 33만까지 쌓였고, 부하가 끝나고 20분이 지나서야 다 빠졌다. 부하가 끝난 뒤에도 초당 290건 정도라 CPU 문제가 아니라 컨슈머 처리 방식 자체가 한계다.

## 컨슈머 스레드 · 파티션 늘리기

서버를 나눈 뒤에도 컨슈머는 CPU 13%로 초당 270건에서 막혔다. 스레드 3개가 한 건에 11ms씩 쓰는 게 그대로 한계라서, 스레드와 파티션을 늘려 봤다.

- 컨슈머 스레드 3 → 10, 토픽 파티션 3 → 20, max.poll.records 500 → 2000
- 나머지는 서버 분리 때와 같음 (VU 1,000, 15분, 재고 60만)

계산대로라면 스레드 10 ÷ 11ms ≈ 900까지 가야 하는데 640에서 멈췄다. 동시에 INSERT하는 수가 늘면서 건당 시간이 11ms에서 15ms로 늘었고, MySQL 실행 중 쿼리도 5~17개로 올랐다. 인프라 서버 CPU도 최고 78%까지 올라갔다.

부하가 끝나고 API 조회가 없어지자 컨슈머가 초당 800건까지 빨라졌다. 부하 중에는 같은 MySQL을 API 조회(초당 980)와 컨슈머 INSERT가 나눠 쓰느라 서로 느려진 것 같다. API도 커넥션 대기가 자주 튀고 최대 응답이 2.45s로 늘었다. 다음 병목은 DB로 보인다.

## 쿠폰 정보 캐시

컨슈머 스레드를 10개로 늘리자 MySQL 하나를 API의 쿠폰 조회(초당 약 980)와 컨슈머 INSERT(초당 약 640)가 같이 쓰면서 서로 느려졌다. 컨슈머 건당 처리 시간은 11ms에서 15ms로 늘었고, API 커넥션 대기는 150~185까지 튀었다. 부하가 끝나 조회가 없어지자 컨슈머는 초당 800건으로 빨라졌다.

쿠폰 수량은 바뀌지 않는 값인데 발급 요청마다 DB에서 읽고 있었다. DB 서버를 따로 떼기 전에 이 조회부터 없애 보려고, 수량을 Redis에 캐시해서 발급 요청이 DB를 거치지 않게 했다.

```
전   요청 → MySQL 쿠폰 조회 → Redis SADD · INCR → Kafka
후   요청 → Redis 수량 GET · SADD · INCR → Kafka
           (캐시에 없을 때만 MySQL에서 읽어서 넣음, TTL 12시간)
```

- 나머지는 스레드 10 때와 같음 (서버 5대, 컨슈머 스레드 10, 파티션 20, VU 1,000, 15분, 재고 60만)

API 커넥션 대기랑 MySQL 조회가 없어지는지, 컨슈머가 640보다 빨라지는지 본다. 컨슈머가 안 빨라지면 INSERT 자체가 다음 한계라는 뜻이라 그때 DB 분리나 MySQL 설정을 본다.

컨슈머는 기대만큼 빨라지지 않았다. 부하 중 630~640에서 660~690으로 조금 올랐고 건당 처리 시간도 14~15ms 그대로였다. 인프라 서버 CPU가 78%에서 51%로 내려갔는데도 그대로라, API 조회와 MySQL을 나눠 쓴 게 주원인은 아니었다. 부하가 끝난 뒤 빨라진 폭도 지난번(640 → 800)보다 작았다.

컨슈머 스레드 10개가 커넥션 10개를 다 쓰고 대기는 0이라, 커넥션 수가 아니라 INSERT 한 건에 걸리는 시간이 한계다. CPU가 남는데 한 건에 14ms씩 걸리니 커밋할 때마다 디스크에 쓰는 시간을 의심하고 있다. 다음 병목은 MySQL INSERT로 보인다.

## MySQL 커밋 설정

캐시로 API 조회를 없앴는데도 컨슈머는 INSERT 한 건에 14~15ms씩 걸렸다. 인프라 서버 CPU는 51%로 여유가 있어서, CPU가 아니라 커밋할 때마다 redo 로그를 디스크에 쓰고(fsync) 기다리는 시간을 의심했다. MySQL 기본값은 커밋마다 디스크에 쓴다.

`innodb_flush_log_at_trx_commit` 1 → 2

```
1 (기본)   커밋 → redo 로그를 디스크에 쓰고 기다림 → 커밋 끝
2          커밋 → OS 버퍼에만 씀 → 커밋 끝      디스크에는 1초마다 한 번씩
```

MySQL만 죽으면 잃는 건 없지만, 서버(OS)가 통째로 죽으면 마지막 1초 정도의 커밋을 잃을 수 있다.

- 나머지는 캐시 때와 같음 (서버 5대, 컨슈머 스레드 10, 파티션 20, VU 1,000, 15분, 재고 60만, sync_binlog 1 그대로)

컨슈머 건당 처리 시간이 14~15ms보다 줄어드는지, 그만큼 컨슈머 TPS가 오르고 Lag가 줄어드는지 본다.

설정 하나로 컨슈머 건당 처리 시간이 14~15ms에서 8ms로 반쯤 줄었다. 커밋할 때 redo 로그를 디스크에 쓰고 기다리던 시간이 그만큼이었다. 스레드 10개로 초당 1,250건 가까이 넣을 수 있게 되면서 발행(초당 약 990)을 그대로 따라갔고, Lag는 최대 223으로 거의 안 쌓였다.

대신 인프라 서버가 바빠졌다. INSERT가 초당 680에서 980으로 늘면서 인프라 CPU가 51%에서 72%로 올랐다. API는 중앙값은 그대로인데 p95가 12.4ms에서 23.9ms로, 최대가 780ms로 늘었다. 같은 서버에 있는 Redis · Kafka 응답이 가끔 늦어진 탓으로 보인다.

이 설정은 서버(OS)가 통째로 죽으면 마지막 1초 정도의 커밋을 잃을 수 있다. 그러면 Redis에는 발급됐는데 DB에는 없는 쿠폰이 생기니, Redis 발급 셋과 DB를 맞춰 보는 보정이 같이 있어야 한다.

VU 1,000에서는 이제 API도 컨슈머도 다 받아 낸다. 다음은 VU를 올려서 새 한계를 찾는다.

## 컨슈머 스레드 · 파티션 · 커넥션 풀 늘리기

VU 5,000에서 컨슈머가 초당 1,200건 정도에서 막혀 Lag가 132만까지 쌓였고, 다 빠지는 데 18분이 걸렸다. 건당 처리 시간은 8ms 그대로였고 컨슈머 서버 CPU도 최고 37%로 여유가 있어서, 서버를 늘리기 전에 컨슈머 설정을 튜닝해서 Lag를 줄여 보려고 한다.

- 컨슈머 스레드 10 → 15, 토픽 파티션 20 → 30, 컨슈머 DB 커넥션 풀 10 → 15
- 스레드 하나가 커넥션 하나로 INSERT하니, 커넥션 풀(기본 10)도 스레드 수만큼 같이 늘렸다
- 파티션은 스레드마다 2개씩 고르게 나눠 갖도록 30개
- 나머지는 VU 5,000 때와 같음 (서버 5대, 17분 계단, 재고 300만, innodb_flush_log_at_trx_commit 2)

```
전   스레드 10 × 파티션 2개씩 (20)   커넥션 10    10 ÷ 8ms ≈ 1,250/s
후   스레드 15 × 파티션 2개씩 (30)   커넥션 15    15 ÷ 8ms ≈ 1,875/s   건당 시간이 그대로라면
```

스레드를 늘려도 건당 8ms가 유지되는지 본다. 동시에 INSERT하는 수가 늘면서 건당 시간이 늘어나면 MySQL이 다음 병목이다.

컨슈머가 부하 중 초당 1,200건에서 1,470건 정도로 올랐고, Lag는 132만에서 114만으로, 다 빠지는 시간은 18분에서 11분으로 줄었다. 커넥션 15개를 다 쓰면서 대기는 0이라 풀은 스레드 수에 맞게 잘 늘었다.

그런데 스레드를 1.5배로 늘렸는데 처리량은 1.2배만 늘었다. 건당 처리 시간이 8ms에서 10ms로 늘었기 때문이다(15 ÷ 10ms ≈ 1,500). 동시에 INSERT하는 수가 늘면서 MySQL 실행 중 쿼리가 12개에서 17개로 올랐고, 인프라 서버 CPU도 최고 68%에서 78%로 올랐다. 컨슈머 서버 CPU는 39%라 컨슈머는 MySQL을 기다리고 있었다.

부하가 끝나자 건당 시간이 8.7ms로 줄고 처리량이 초당 1,710건으로 올랐다. API 요청이 멈춰서 같은 인프라 서버의 Kafka · Redis가 한가해지자 MySQL이 빨라진 것이다. 스레드 10일 때는 부하가 끝나도 거의 그대로였는데, MySQL이 바빠지면서 Kafka · Redis와 자원을 나눠 쓰는 영향이 드러났다.

컨슈머 스레드나 컨슈머 서버를 더 늘려도 MySQL에서 기다리는 시간이 더 늘 뿐이다. 다음은 MySQL을 인프라 서버에서 떼어 CPU와 디스크를 따로 주는 DB 서버 분리다.

## DB 서버 분리

컨슈머 스레드를 15개로 늘리자 건당 처리 시간이 8ms에서 10ms로 늘었고 MySQL 실행 중 쿼리도 17개까지 올랐다. 부하가 끝나 같은 인프라 서버의 Kafka · Redis가 한가해지자 건당 8.7ms, 초당 1,710건으로 바로 빨라졌다. MySQL이 Kafka · Redis와 한 서버에서 CPU와 디스크를 나눠 쓰는 게 걸린다고 보고, MySQL을 따로 떼어 낸다.

```
전   인프라 (t3.medium)   MySQL · Redis · Kafka
후   인프라 (t3.medium)   Redis · Kafka
```

- MySQL 설정은 그대로 (버퍼 풀 256M, innodb_flush_log_at_trx_commit 2). 서버를 나눈 효과만 본다
- API · 컨슈머는 DB 주소만 DB 서버로 바꾸고, Redis · Kafka는 인프라 서버 그대로
- 나머지는 컨슈머 스레드 15 때와 같음 (VU 5,000 17분 계단, 재고 300만, 컨슈머 스레드 15, 파티션 30, 커넥션 풀 15)

MySQL을 떼어 내니 컨슈머가 초당 1,470건에서 2,150건 정도로 올랐고, Lag는 114만에서 70만으로, 다 빠지는 시간은 11분에서 6분으로 줄었다. 건당 처리 시간이 부하 중에도 7ms로, 부하가 끝난 뒤와 차이가 없어졌다. 지난번에 부하 중(10ms)과 부하 끝(8.7ms)이 달랐던 게 Kafka · Redis와 자원을 나눠 쓴 몫이었다.

인프라 서버 CPU는 78%에서 27%로 내려갔다. 인프라 서버 일의 대부분이 MySQL이었고, Redis · Kafka는 초당 3,800건을 받아도 27%면 충분했다. DB 서버 CPU는 최고 69%였다.

이번에는 대시보드에 있는 MySQL 지표(초당 쿼리 수, 실행 중 쿼리)만 보고 여기까지 판단했다. CloudWatch로 DB 서버 CPU가 69%까지 오른 건 알았지만, 버퍼 풀이 모자라서 디스크를 읽는지, 커밋할 때 디스크를 얼마나 기다리는지는 대시보드로는 알 수 없었다. 그래서 다음 튜닝을 지표를 보고 고를 수 있게 대시보드에 "DB 서버" 줄을 추가했다. DB 서버 CPU, 디스크 쓰기 횟수와 한 번 걸린 시간(node-exporter), 버퍼 풀에 없어 디스크에서 읽은 횟수, redo · 데이터 파일 fsync, 로그 버퍼 대기(mysqld-exporter)를 본다.

컨슈머는 아직 들어오는 양(초당 약 3,800)을 다 따라가지 못하고, API는 VU 3,500쯤부터 톰캣 스레드 200개가 다 차고 CPU가 95% 가까이 올라 p95가 820ms 정도다.

## 컨슈머 스레드 30

DB를 떼어 낸 뒤 컨슈머는 건당 7ms로 부하 중에도 일정했지만, 스레드 15개로는 초당 2,150건 정도가 끝이라 들어오는 양(초당 약 3,800)을 못 따라갔다. 컨슈머 서버 CPU는 50%, DB 서버 CPU는 69%로 둘 다 아직 여유가 있어서 스레드를 더 늘려 본다.

- 컨슈머 스레드 15 → 30, 컨슈머 DB 커넥션 풀 15 → 30
- 토픽 파티션은 30 그대로라 스레드 하나가 파티션 하나씩 맡는다
- 나머지는 DB 서버 분리 때와 같음 (서버 6대, VU 5,000 17분 계단, 재고 300만)

```
전   스레드 15 × 파티션 2개씩   커넥션 15   15 ÷ 7ms ≈ 2,150/s
후   스레드 30 × 파티션 1개씩   커넥션 30   30 ÷ 7ms ≈ 4,300/s   건당 시간이 그대로라면
```

INSERT가 늘면 DB 서버가 바빠져서 건당 시간이 늘어날 수 있다. 이번에 추가한 "DB 서버" 대시보드로 DB 서버 CPU, 디스크 쓰기 한 번 걸린 시간, 버퍼 풀, fsync 중 무엇이 먼저 한계에 닿는지 본다.

스레드를 두 배로 늘렸는데 컨슈머는 초당 2,150건에서 2,500건 정도로 1.17배만 늘었다. VU 2,500까지는 건당 7~9ms로 발행을 따라갔지만, 그 뒤로는 건당 12ms로 늘면서 초당 2,500건에서 멈췄다(30 ÷ 12ms ≈ 2,500). MySQL 실행 중 쿼리가 32개라 컨슈머 30개가 전부 MySQL 안에서 차례를 기다리고 있었다. Lag는 70만에서 49만으로, 다 빠지는 시간은 6분에서 3분 반으로 줄었다.

이번에는 추가한 DB 서버 지표로 원인을 좁혀 볼 수 있었다. 디스크 쓰기 한 번은 0.92~0.97ms로 부하 내내 거의 같았고, 버퍼 풀과 로그 버퍼도 모자라지 않았다. 처리량이 멈춘 시점에 같이 평평해진 건 DB 서버 CPU 하나였다. 실제로 계산에 쓴 시간이 66% 정도(user · system · softirq), 디스크를 기다린 시간이 17%로, 남은 건 16% 정도였다. 부하가 끝난 뒤에도 초당 2,500건 · 건당 12ms 그대로라 다른 서버와의 다툼이 아니라 DB 서버(t3.small, vCPU 2개) 자체의 한계로 보인다.

softirq가 14%나 되는 건 INSERT마다 트랜잭션 시작 · INSERT · 커밋으로 작은 패킷이 오가서, 그걸 처리하는 데 CPU를 쓰는 것으로 보인다. 지난번에 디스크 대기열(약 0.94)과 쓰기 횟수(초당 약 1,030)로 어림한 디스크 한 번 약 0.9ms는 직접 잰 값과 맞았다.

저장 쪽은 DB 서버 CPU가 한계라 컨슈머를 더 늘려도 소용이 없다. API는 그대로 VU 3,500쯤부터 톰캣 스레드 200개가 다 차고 CPU가 95% 넘게 올라 p95가 830ms 정도다.

## DB · API 서버 키우기

컨슈머 스레드 30에서 저장 쪽은 DB 서버(t3.small, vCPU 2개) CPU가, 요청 쪽은 API 서버(t3.medium, vCPU 2개) CPU가 한계였다. 둘 다 CPU가 모자란 것이라 vCPU를 늘린다. 두 길은 Kafka로 나뉘어 있고 API는 발급 때 DB를 쓰지 않아서, 같이 키워도 효과를 길별로 나눠 볼 수 있다.

```
요청 쪽   k6 ──▶ API ──▶ Redis · Kafka ──▶ 202        API를 키우면 톰캣 · API CPU · 응답 시간이 바뀜
저장 쪽   Kafka ──▶ 컨슈머 ──▶ DB                     DB를 키우면 건당 처리 시간 · 컨슈머 처리량 · DB CPU가 바뀜
```

| 서버 | 전 | 후 |
|---|---|---|
| DB | t3.small (vCPU 2) | t3.xlarge (vCPU 4) |
| API | t3.medium (vCPU 2) | t3.xlarge (vCPU 4) |
| k6 | t3.medium | t3.xlarge |

- API가 빨라지면 k6가 보내는 요청도 늘어서(VU 5,000에서 초당 5,000건 가까이) k6 서버 CPU가 먼저 찰 수 있다. 측정이 흔들리지 않게 k6 서버도 같이 키운다
- 앱 · MySQL 설정은 그대로 (컨슈머 스레드 30 · 풀 30, 파티션 30, 버퍼 풀 256M, flush 2, API 힙 512M, 톰캣 스레드 200)
- 인프라 · 컨슈머 t3.medium, 모니터링 t3.small 그대로. VU 5,000 17분 계단, 재고 300만

요청 쪽은 톰캣 줄이 사라지고 응답 시간이 줄어드는지, 저장 쪽은 건당 처리 시간이 7ms 쪽으로 돌아가 컨슈머 처리량이 오르는지 본다. API가 받는 양이 늘어서 Kafka에 들어오는 양도 늘기 때문에, 저장 쪽은 Lag보다 컨슈머 처리량과 건당 시간으로 비교한다. 컨슈머 서버 CPU와 인프라 서버 CPU가 다음 한계가 되는지도 본다.

요청 쪽은 API 서버를 키우자 바로 풀렸다. API CPU가 96%에서 66%로 내려가 톰캣 스레드에 줄이 거의 안 생겼고, 서버 응답이 40ms 안팎에서 9ms 정도로 줄었다. k6 p95는 827ms에서 70ms로 줄었고, 응답이 빨라진 만큼 같은 17분 동안 요청을 48만 건 더 보냈다(한 바퀴 평균 1.02초). 지난번 요청 쪽 병목이 API CPU였다는 게 확인됐다. VU 5,000 구간에서 톰캣이 가끔 200까지 튀는 건 남아 있다.

저장 쪽은 DB 서버 CPU를 두 배로 늘렸는데 컨슈머는 초당 2,500건에서 2,780건으로 1.1배만 늘었다. DB 서버 CPU는 21%가 남아 있어서 이번에는 CPU가 한계가 아니다. 디스크 쓰기 한 번은 0.97ms로 그대로였지만 초당 920번을 쓰니 디스크가 쉬지 않고 쓰는 비율이 0.89 정도(920 × 0.97ms)다. 커밋할 때마다 binlog를 디스크에 쓰고 기다리는 길이 한 줄로 거의 꽉 찬 것으로 보인다. 지난번에 "디스크 한 번 시간이 그대로라 디스크는 여유"라고 봤는데, 그때도 이미 0.79(820 × 0.96ms)였다. CPU가 먼저 차서 가려져 있던 것이다. MySQL 안에서 같은 페이지에 동시에 쓰려는 다툼일 수도 있는데, 이건 지금 지표로는 가를 수 없다.

API가 더 많이 받아서 Kafka에 들어오는 양도 초당 4,850건 정도로 늘었고, 그래서 Lag는 82만으로 오히려 커졌다. 컨슈머 서버(CPU 61%)와 인프라 서버(49%), k6 서버(55%)는 아직 여유가 있다.

요청 쪽은 서버를 키워서 풀렸다. 저장 쪽은 CPU를 더 줘도 안 오르니, 커밋을 한 건씩 하는 방식 자체를 바꾸는 쪽(여러 건을 한 번에 커밋)이 다음 후보다.
