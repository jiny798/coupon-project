# 부하 테스트 결과

## 환경

- AWS 서울 리전, t3.medium 2대 (같은 서브넷)
- 앱 서버 1대에 api, consumer, MySQL, Redis, Kafka, Prometheus, Grafana를 전부 컨테이너로 올림
- k6 서버에서 앱 서버 사설 IP로 부하를 줌
- Rate Limiter 없음

발급 흐름은 Redis로 중복이랑 순번을 판정하고, Kafka에 발행해서 ack를 받으면 202를 준다. DB 저장은 컨슈머가 따로 한다.

통과 기준은 k6 threshold 그대로 성공 응답 99% 이상, p95 10초 이하.

## VU 500, VU 1,000 (OSIV 켜진 상태)

| | VU 500 (1-1) | VU 1,000 (1-2) |
|---|---|---|
| 결과 | 통과 | 통과. OSIV 끄고 다시 잰 결과는 아래 |
| 부하 | 0 → 100 → 400 → 500, 12분 | 0 → 100 → 400 → 700 → 1,000, 15분 |
| 재고 | 10만 | 60만 |
| 요청 수 / 실패 | 248,733 / 0 | 421,201 / 0 |
| p95 (k6) | 55ms | 1.03s |
| API TPS | 평균 345, 발급 구간 최대 약 415 | 평균 465, 최대 709 (650~680에서 더 안 올라감) |
| 컨슈머 TPS | 최대 258 (250 근처에서 평평) | 최대 254, VU 700 넘어서는 약 210 |
| Lag 최대 | 28K, 매진 후 2분쯤 지나 0 | 247K, 부하 끝나고 14분쯤 지나 0 |
| 앱 서버 CPU | 최고 76% | 96% |
| 특징 | 컨슈머가 초당 250건 정도에서 막혀서 Lag가 쌓임. 매진 직전에 API DB 커넥션 대기가 잠깐 190 가까이 튐 | 톰캣 스레드 200개가 다 참. API DB 커넥션 10개를 다 쓰고 190개 정도가 대기. CPU도 거의 다 씀 |
| 발급 수량 | 100,000장 (DB, Redis 같음) | 421,201장 (DB, Redis 같음) |

- VU 500은 재고 10만이 중간에 다 나가서 500 VU 구간은 매진 응답만 받았다. API 최대 496/s도 매진 응답 기준이라 표에는 발급 구간 값을 적었다.
- VU 1,000은 15분 동안 계속 발급되게 재고를 60만으로 잡았다.

## API DB 커넥션 대기

VU 1,000에서 VU 700을 넘어가면서 이렇게 됐다.

| 항목 | 값 |
|---|---|
| 톰캣 스레드 | 200 / 200 |
| API DB 커넥션 | 10 / 10 사용, 약 190 대기 |
| MySQL 실행 중 쿼리 | 4~7개 |

MySQL에서 한 번에 처리 중인 쿼리는 4~7개뿐이라 DB가 밀린 건 아니었는데 커넥션이 모자랐다. 커넥션 10개로 초당 670건 정도를 처리했으니 요청 하나가 커넥션을 15ms쯤 잡고 있었던 셈이다. 쿠폰 조회 한 번은 1ms도 안 걸린다.

원인은 OSIV(open-in-view)로 봤다. 기본값이 켜져 있어서 쿠폰 조회 때 가져간 커넥션을 요청이 끝날 때까지 들고 있는다. 그 사이에 Redis 호출이랑 Kafka ack 기다리는 시간도 다 들어간다.

```
OSIV 켜짐   조회 ── 커넥션 ═════════════════════════ 요청 끝날 때 반납
                     (Redis, Kafka ack 기다리는 동안에도 들고 있음)
OSIV 꺼짐   조회 ── 커넥션 ═ 바로 반납
```

VU 500 때도 같은 상황이었다. 매진 직전에 발급이 초당 415건 정도일 때 커넥션 대기가 잠깐 190 가까이 올라갔다.
그런데 매진 뒤에는 매진 응답을 초당 490건 정도로 더 많이 처리했는데도 대기가 없었다. 매진 응답은 Kafka를 안 거치니까, Kafka ack를 기다리는 동안 커넥션을 들고 있는 게 큰 것 같다.

## OSIV 끄기

`spring.jpa.open-in-view: false`

VU 1,000, 1-2와 같은 조건 (15분, 재고 60만)

| | OSIV 켜짐 (1-2) | OSIV 꺼짐 |
|---|---|---|
| 결과 | 통과 | 통과 |
| 요청 수 / 실패 | 421,201 / 0 | 510,029 / 0 |
| p95 (k6) | 1.03s | 315ms |
| 응답 평균 / 중앙값 (k6) | 297ms / 154ms | 70ms / 30ms |
| API TPS | 평균 465, 최대 709 (650~680에서 멈춤) | 평균 564, 최대 916 (VU 따라 올라감) |
| API DB 커넥션 | 10 / 10, 대기 약 190이 계속 | 대기가 0~180 사이를 오르내림 |
| 앱 서버 CPU (CloudWatch) | 96% | 95% (VU 1,000 구간 5분 평균, 최고 99.5%) |
| 컨슈머 TPS | 최대 254, 부하 중 약 210 | 최대 288, 부하 중 약 210, 부하 끝나고 약 320 |
| Lag 최대 | 247K, 부하 끝나고 14분쯤 지나 0 | 약 32만, 부하 끝나고 17분 반쯤 지나 0 |
| 발급 수량 | 421,201장 | 510,029장 (DB, Redis 같음) |

OSIV를 끄니까 커넥션 때문에 막혀 있던 680/s 천장이 없어졌다. API TPS가 VU 1,000에서 900 정도까지 VU를 따라 올라갔고, p95는 1.03s에서 315ms로 줄었다.
응답이 빨라진 만큼 k6가 같은 15분 동안 9만 건 가까이 더 보냈다 (한 바퀴 평균 1.29초 → 1.07초).

대신 앱 서버 CPU가 100% 가까이 찼다. 커넥션 대기도 완전히 없어지진 않고 가끔 튀었는데, CPU가 꽉 차서 커넥션을 쥔 스레드가 늦게 끝나는 것 같다. 다음 병목은 CPU로 보인다.

API가 더 많이 받은 만큼 Kafka에도 더 많이 쌓였다. 컨슈머는 부하 중에 초당 210건 정도로 그대로라 Lag가 32만까지 갔고, 부하가 끝나 CPU가 풀리자 초당 320건 정도로 빨라졌다.

## 서버 분리

VU를 1,000으로 올리니 앱 서버 CPU가 95% 넘게 차면서 API 응답이 늦어졌고(p95 315ms), 같은 서버의 컨슈머도 느려져서 Lag가 32만까지 쌓였다. API, 컨슈머, DB, Kafka가 한 서버에서 CPU를 나눠 쓰는 게 원인으로 보여서 서버를 나눠 보려고 한다.

```
k6 ──8080──▶ API ──3306 · 6379 · 9092──▶ 인프라 (MySQL · Redis · Kafka)
                                           ▲
                          컨슈머 ──────────┘
모니터링 (Prometheus · Grafana) ── API · 컨슈머 · 인프라 수집
```

- t3.medium 4대 (API, 인프라, 컨슈머, k6) + t3.small 1대 (모니터링), 같은 서브넷
- MySQL · Kafka · JVM 메모리 설정은 한 대일 때와 같게 두고 서버만 나눴다
- OSIV 꺼짐, Rate Limiter 없음

VU 1,000, 같은 조건 (15분, 재고 60만)

| | 한 대 (OSIV 꺼짐) | 서버 분리 |
|---|---|---|
| 결과 | 통과 | 통과 |
| 요청 수 / 실패 | 510,029 / 0 | 535,975 / 0 |
| p95 (k6) | 315ms | 26.5ms |
| 응답 평균 / 중앙값 (k6) | 70ms / 30ms | 18.7ms / 7.5ms |
| API TPS | 평균 564, 최대 916 | 평균 593, 최대 990 |
| CPU (CloudWatch, VU 1,000 구간 5분 평균) | 앱 서버 95% | API 64%, 인프라 62%, 컨슈머 13%, k6 26% |
| 컨슈머 TPS | 최대 288, 부하 중 약 210 | 최대 277, 부하 중 260~270, 부하 끝나고 약 290 |
| Lag 최대 | 약 32만, 부하 끝나고 17분 반쯤 지나 0 | 약 33만, 부하 끝나고 20분쯤 지나 0 |
| 발급 수량 | 510,029장 | 535,975장 (DB, Redis 같음) |

서버를 나누니 API는 VU 1,000을 다 받아 냈다. 한 바퀴 평균이 1.01초라 이론상 최대(546,000 ÷ 1초)에 가깝게 보냈고, p95는 315ms에서 26.5ms로 줄었다. API 서버 CPU 64%, 인프라 서버 62%라 아직 여유가 있다.

컨슈머는 서버를 따로 줬는데도 초당 270건 정도에서 더 안 올라갔다. 컨슈머 서버 CPU는 13%뿐이었다. 스레드 3개가 한 건에 11ms 정도씩 쓰니까 3 ÷ 0.011 ≈ 270이 그대로 한계다. API가 초당 990건을 넣는 동안 Lag가 33만까지 쌓였고, 부하가 끝나고 20분이 지나서야 다 빠졌다. 부하가 끝난 뒤에도 초당 290건 정도라 CPU 문제가 아니라 컨슈머 처리 방식 자체가 한계다.
