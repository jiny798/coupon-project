# 부하 테스트 결과

## 목표

가장 몰릴 때 1초에 10,000명이 쿠폰을 누르고, 그 상태가 5분 동안 이어진다. 앞뒤로 천천히 늘고 주는 시간까지 합치면 17분 동안 약 560만 명이다(재고를 넉넉히 둬서 모두 발급되는, 저장 쪽에 가장 힘든 경우). 이때

| # | 항목 | 목표 | 어디서 재나 |
|---|---|---|---|
| 1 | 응답 시간 | p90 1초, p95 2초 이내 | k6 |
| 2 | 실패 | 0건 | k6 `http_req_failed` |
| 3 | 받아 낸 양 | 1초 10,000명 구간에서 초당 9,500건 이상 | API TPS |
| 4 | DB 저장까지 | 발급 응답 뒤 가장 늦은 것도 60초 이내 | 컨슈머가 잰 발행 → 저장 시간 |
| 5 | 정합성 | 발급 수량 = Redis 셋 = Redis 순번 = DB = k6 요청 수 | 끝난 뒤 확인 |
| 6 | 서버 여유 | 가장 바쁜 서버도 CPU 80% 이하 | CloudWatch |
| 7 | 측정 신뢰 | k6 서버 CPU 80% 이하 | vmstat · CloudWatch |

- 응답 목표는 큰 이벤트라 1~2초는 기다릴 수 있다고 보고 잡았다. 대신 k6는 서버가 느리면 덜 보내서 응답이 어느 선에서 멈춘 것처럼 보이는데, 실제로는 사람이 계속 오니 처리량이 도착량보다 작으면 줄이 끝없이 늘어난다. 그래서 받아 낸 양(3)을 같이 본다.
- DB 저장 60초는 발급 응답을 받고 쿠폰함을 열었을 때 1분 안에는 보여야 한다고 보고 잡았다. 5분 동안 초당 10,000건이 들어올 때 이걸 지키려면 컨슈머가 초당 약 8,330건 이상 저장해야 한다.
- 실제 오픈은 정각에 훨씬 뾰족하게 몰리고 재고가 작아 금방 매진된다. 여기 목표는 오래, 꾸준히, 전부 저장까지 가는 경우 기준이다.
- 처음에는 1초에 5,000명(17분 약 280만 명, 받아 낸 양 4,750건, 컨슈머 4,040건) 기준으로 잡았다. 배치 INSERT까지 와서 서버 여유(6) 말고는 모두 달성해서 1초 10,000명으로 올렸다.

## 환경

- AWS 서울 리전, t3.medium 2대 (같은 서브넷)
- 앱 서버 1대에 api, consumer, MySQL, Redis, Kafka, Prometheus, Grafana를 전부 컨테이너로 올림
- k6 서버에서 앱 서버 사설 IP로 부하를 줌
- Rate Limiter 없음

발급 흐름은 Redis로 중복이랑 순번을 판정하고, Kafka에 발행해서 ack를 받으면 202를 준다. DB 저장은 컨슈머가 따로 한다.

통과 기준은 k6 threshold 그대로 성공 응답 99% 이상, p95 10초 이하.

## API DB 커넥션 대기

VU 1,000에서 VU 700을 넘어가면서 이렇게 됐다.

| 항목 | 값 |
|---|---|
| 톰캣 스레드 | 200 / 200 |
| API DB 커넥션 | 10 / 10 사용, 약 190 대기 |
| MySQL 실행 중 쿼리 | 4~7개 |

MySQL에서 한 번에 처리 중인 쿼리는 4~7개뿐이라 DB가 밀린 건 아니었는데 커넥션이 모자랐다. 커넥션 10개로 초당 670건 정도를 처리했으니 요청 하나가 커넥션을 15ms쯤 잡고 있었던 셈이다. 쿠폰 조회 한 번은 1ms도 안 걸린다.

원인은 OSIV(open-in-view)로 봤다. 기본값이 켜져 있어서 쿠폰 조회 때 가져간 커넥션을 요청이 끝날 때까지 들고 있는다. 그 사이에 Redis 호출이랑 Kafka ack 기다리는 시간도 다 들어간다.

```
OSIV 켜짐   조회 ── 커넥션 ═════════════════════════ 요청 끝날 때 반납
                     (Redis, Kafka ack 기다리는 동안에도 들고 있음)
OSIV 꺼짐   조회 ── 커넥션 ═ 바로 반납
```

VU 500 때도 같은 상황이었다. 매진 직전에 발급이 초당 415건 정도일 때 커넥션 대기가 잠깐 190 가까이 올라갔다.
그런데 매진 뒤에는 매진 응답을 초당 490건 정도로 더 많이 처리했는데도 대기가 없었다. 매진 응답은 Kafka를 안 거치니까, Kafka ack를 기다리는 동안 커넥션을 들고 있는 게 큰 것 같다.

응답이 빨라진 만큼 k6가 같은 15분 동안 9만 건 가까이 더 보냈다 (한 바퀴 평균 1.29초 → 1.07초).

API가 더 많이 받은 만큼 Kafka에도 더 많이 쌓였다. 컨슈머는 부하 중에 초당 210건 정도로 그대로라 Lag가 32만까지 갔고, 부하가 끝나 CPU가 풀리자 초당 320건 정도로 빨라졌다.

## 서버 분리

VU를 1,000으로 올리니 앱 서버 CPU가 95% 넘게 차면서 API 응답이 늦어졌고(p95 315ms), 같은 서버의 컨슈머도 느려져서 Lag가 32만까지 쌓였다. API, 컨슈머, DB, Kafka가 한 서버에서 CPU를 나눠 쓰는 게 원인으로 보여서 서버를 나눠 보려고 한다.

```
k6 ──8080──▶ API ──3306 · 6379 · 9092──▶ 인프라 (MySQL · Redis · Kafka)
                                           ▲
                          컨슈머 ──────────┘
모니터링 (Prometheus · Grafana) ── API · 컨슈머 · 인프라 수집
```

- t3.medium 4대 (API, 인프라, 컨슈머, k6) + t3.small 1대 (모니터링), 같은 서브넷
- MySQL · Kafka · JVM 메모리 설정은 한 대일 때와 같게 두고 서버만 나눴다
- OSIV 꺼짐, Rate Limiter 없음

컨슈머는 서버를 따로 줬는데도 초당 270건 정도에서 더 안 올라갔다. 컨슈머 서버 CPU는 13%뿐이었다. 스레드 3개가 한 건에 11ms 정도씩 쓰니까 3 ÷ 0.011 ≈ 270이 그대로 한계다. API가 초당 990건을 넣는 동안 Lag가 33만까지 쌓였고, 부하가 끝나고 20분이 지나서야 다 빠졌다. 부하가 끝난 뒤에도 초당 290건 정도라 CPU 문제가 아니라 컨슈머 처리 방식 자체가 한계다.

## 컨슈머 스레드 · 파티션 늘리기

서버를 나눈 뒤에도 컨슈머는 CPU 13%로 초당 270건에서 막혔다. 스레드 3개가 한 건에 11ms씩 쓰는 게 그대로 한계라서, 스레드와 파티션을 늘려 봤다.

- 컨슈머 스레드 3 → 10, 토픽 파티션 3 → 20, max.poll.records 500 → 2000
- 나머지는 서버 분리 때와 같음 (VU 1,000, 15분, 재고 60만)

컨슈머가 초당 270건에서 640건 정도로 2배 넘게 빨라졌다. Lag는 33만에서 12만으로 줄었고, 다 빠지는 데 걸린 시간도 20분에서 3분으로 줄었다. VU 700까지는 처리가 발행을 그대로 따라갔다.

계산대로라면 스레드 10 ÷ 11ms ≈ 900까지 가야 하는데 640에서 멈췄다. 동시에 INSERT하는 수가 늘면서 건당 시간이 11ms에서 15ms로 늘었고, MySQL 실행 중 쿼리도 5~17개로 올랐다. 인프라 서버 CPU도 최고 78%까지 올라갔다.

부하가 끝나고 API 조회가 없어지자 컨슈머가 초당 800건까지 빨라졌다. 부하 중에는 같은 MySQL을 API 조회(초당 980)와 컨슈머 INSERT가 나눠 쓰느라 서로 느려진 것 같다. API도 커넥션 대기가 자주 튀고 최대 응답이 2.45s로 늘었다. 다음 병목은 DB로 보인다.

## 쿠폰 정보 캐시

컨슈머 스레드를 10개로 늘리자 MySQL 하나를 API의 쿠폰 조회(초당 약 980)와 컨슈머 INSERT(초당 약 640)가 같이 쓰면서 서로 느려졌다. 컨슈머 건당 처리 시간은 11ms에서 15ms로 늘었고, API 커넥션 대기는 150~185까지 튀었다. 부하가 끝나 조회가 없어지자 컨슈머는 초당 800건으로 빨라졌다.

쿠폰 수량은 바뀌지 않는 값인데 발급 요청마다 DB에서 읽고 있었다. DB 서버를 따로 떼기 전에 이 조회부터 없애 보려고, 수량을 Redis에 캐시해서 발급 요청이 DB를 거치지 않게 했다.

```
전   요청 → MySQL 쿠폰 조회 → Redis SADD · INCR → Kafka
후   요청 → Redis 수량 GET · SADD · INCR → Kafka
           (캐시에 없을 때만 MySQL에서 읽어서 넣음, TTL 12시간)
```

- 나머지는 스레드 10 때와 같음 (서버 5대, 컨슈머 스레드 10, 파티션 20, VU 1,000, 15분, 재고 60만)

캐시를 넣으니 API는 발급 요청 중에 DB를 한 번도 안 갔다. MySQL select가 0이 됐고 API DB 커넥션은 사용 중도 대기도 0이었다. p95는 29.9ms에서 12.4ms로, 최대 응답은 2.45s에서 169ms로 줄었다. 한 바퀴 평균이 1.00초라 VU 1,000을 거의 그대로 받아 냈다. 수량 캐시는 테스트 시작 직후 첫 요청 때 한 번 채워졌다.

컨슈머는 기대만큼 빨라지지 않았다. 부하 중 630~640에서 660~690으로 조금 올랐고 건당 처리 시간도 14~15ms 그대로였다. 인프라 서버 CPU가 78%에서 51%로 내려갔는데도 그대로라, API 조회와 MySQL을 나눠 쓴 게 주원인은 아니었다. 부하가 끝난 뒤 빨라진 폭도 지난번(640 → 800)보다 작았다.

컨슈머 스레드 10개가 커넥션 10개를 다 쓰고 대기는 0이라, 커넥션 수가 아니라 INSERT 한 건에 걸리는 시간이 한계다. CPU가 남는데 한 건에 14ms씩 걸리니 커밋할 때마다 디스크에 쓰는 시간을 의심하고 있다. 다음 병목은 MySQL INSERT로 보인다.

## MySQL 커밋 설정

캐시로 API 조회를 없앴는데도 컨슈머는 INSERT 한 건에 14~15ms씩 걸렸다. 인프라 서버 CPU는 51%로 여유가 있어서, CPU가 아니라 커밋할 때마다 redo 로그를 디스크에 쓰고(fsync) 기다리는 시간을 의심했다. MySQL 기본값은 커밋마다 디스크에 쓴다.

`innodb_flush_log_at_trx_commit` 1 → 2

```
1 (기본)   커밋 → redo 로그를 디스크에 쓰고 기다림 → 커밋 끝
2          커밋 → OS 버퍼에만 씀 → 커밋 끝      디스크에는 1초마다 한 번씩
```

MySQL만 죽으면 잃는 건 없지만, 서버(OS)가 통째로 죽으면 마지막 1초 정도의 커밋을 잃을 수 있다.

- 나머지는 캐시 때와 같음 (서버 5대, 컨슈머 스레드 10, 파티션 20, VU 1,000, 15분, 재고 60만, sync_binlog 1 그대로)

컨슈머 건당 처리 시간이 14~15ms보다 줄어드는지, 그만큼 컨슈머 TPS가 오르고 Lag가 줄어드는지 본다.

설정 하나로 컨슈머 건당 처리 시간이 14~15ms에서 8ms로 반쯤 줄었다. 커밋할 때 redo 로그를 디스크에 쓰고 기다리던 시간이 그만큼이었다. 스레드 10개로 초당 1,250건 가까이 넣을 수 있게 되면서 발행(초당 약 990)을 그대로 따라갔고, Lag는 최대 223으로 거의 안 쌓였다.

대신 인프라 서버가 바빠졌다. INSERT가 초당 680에서 980으로 늘면서 인프라 CPU가 51%에서 72%로 올랐다. API는 중앙값은 그대로인데 p95가 12.4ms에서 23.9ms로, 최대가 780ms로 늘었다. 같은 서버에 있는 Redis · Kafka 응답이 가끔 늦어진 탓으로 보인다.

이 설정은 서버(OS)가 통째로 죽으면 마지막 1초 정도의 커밋을 잃을 수 있다. 그러면 Redis에는 발급됐는데 DB에는 없는 쿠폰이 생기니, Redis 발급 셋과 DB를 맞춰 보는 보정이 같이 있어야 한다.

VU 1,000에서는 이제 API도 컨슈머도 다 받아 낸다. 다음은 VU를 올려서 새 한계를 찾는다.

## 컨슈머 스레드 · 파티션 · 커넥션 풀 늘리기

VU 5,000에서 컨슈머가 초당 1,200건 정도에서 막혀 Lag가 132만까지 쌓였고, 다 빠지는 데 18분이 걸렸다. 건당 처리 시간은 8ms 그대로였고 컨슈머 서버 CPU도 최고 37%로 여유가 있어서, 서버를 늘리기 전에 컨슈머 설정을 튜닝해서 Lag를 줄여 보려고 한다.

- 컨슈머 스레드 10 → 15, 토픽 파티션 20 → 30, 컨슈머 DB 커넥션 풀 10 → 15
- 스레드 하나가 커넥션 하나로 INSERT하니, 커넥션 풀(기본 10)도 스레드 수만큼 같이 늘렸다
- 파티션은 스레드마다 2개씩 고르게 나눠 갖도록 30개
- 나머지는 VU 5,000 때와 같음 (서버 5대, 17분 계단, 재고 300만, innodb_flush_log_at_trx_commit 2)

```
전   스레드 10 × 파티션 2개씩 (20)   커넥션 10    10 ÷ 8ms ≈ 1,250/s
후   스레드 15 × 파티션 2개씩 (30)   커넥션 15    15 ÷ 8ms ≈ 1,875/s   건당 시간이 그대로라면
```

스레드를 늘려도 건당 8ms가 유지되는지 본다. 동시에 INSERT하는 수가 늘면서 건당 시간이 늘어나면 MySQL이 다음 병목이다.

컨슈머가 부하 중 초당 1,200건에서 1,470건 정도로 올랐고, Lag는 132만에서 114만으로, 다 빠지는 시간은 18분에서 11분으로 줄었다. 커넥션 15개를 다 쓰면서 대기는 0이라 풀은 스레드 수에 맞게 잘 늘었다.

그런데 스레드를 1.5배로 늘렸는데 처리량은 1.2배만 늘었다. 건당 처리 시간이 8ms에서 10ms로 늘었기 때문이다(15 ÷ 10ms ≈ 1,500). 동시에 INSERT하는 수가 늘면서 MySQL 실행 중 쿼리가 12개에서 17개로 올랐고, 인프라 서버 CPU도 최고 68%에서 78%로 올랐다. 컨슈머 서버 CPU는 39%라 컨슈머는 MySQL을 기다리고 있었다.

컨슈머 스레드나 컨슈머 서버를 더 늘려도 MySQL에서 기다리는 시간이 더 늘 뿐이다. 다음은 MySQL을 인프라 서버에서 떼어 CPU와 디스크를 따로 주는 DB 서버 분리다.

## DB 서버 분리

컨슈머 스레드를 15개로 늘리자 건당 처리 시간이 8ms에서 10ms로 늘었고 MySQL 실행 중 쿼리도 17개까지 올랐다. 부하가 끝나 같은 인프라 서버의 Kafka · Redis가 한가해지자 건당 8.7ms, 초당 1,710건으로 바로 빨라졌다. MySQL이 Kafka · Redis와 한 서버에서 CPU와 디스크를 나눠 쓰는 게 걸린다고 보고, MySQL을 따로 떼어 낸다.

```
전   인프라 (t3.medium)   MySQL · Redis · Kafka
후   인프라 (t3.medium)   Redis · Kafka
```

- API · 컨슈머는 DB 주소만 DB 서버로 바꾸고, Redis · Kafka는 인프라 서버 그대로
- 나머지는 컨슈머 스레드 15 때와 같음 (VU 5,000 17분 계단, 재고 300만, 컨슈머 스레드 15, 파티션 30, 커넥션 풀 15)

인프라 서버 CPU는 78%에서 27%로 내려갔다. 인프라 서버 일의 대부분이 MySQL이었고, Redis · Kafka는 초당 3,800건을 받아도 27%면 충분했다. DB 서버 CPU는 최고 69%였다.

이번에는 대시보드에 있는 MySQL 지표(초당 쿼리 수, 실행 중 쿼리)만 보고 여기까지 판단했다. CloudWatch로 DB 서버 CPU가 69%까지 오른 건 알았지만, 버퍼 풀이 모자라서 디스크를 읽는지, 커밋할 때 디스크를 얼마나 기다리는지는 대시보드로는 알 수 없었다. 그래서 다음 튜닝을 지표를 보고 고를 수 있게 대시보드에 "DB 서버" 줄을 추가했다. DB 서버 CPU, 디스크 쓰기 횟수와 한 번 걸린 시간(node-exporter), 버퍼 풀에 없어 디스크에서 읽은 횟수, redo · 데이터 파일 fsync, 로그 버퍼 대기(mysqld-exporter)를 본다.

컨슈머는 아직 들어오는 양(초당 약 3,800)을 다 따라가지 못하고, API는 VU 3,500쯤부터 톰캣 스레드 200개가 다 차고 CPU가 95% 가까이 올라 p95가 820ms 정도다.

## DB · API 서버 키우기

컨슈머 스레드 30에서 저장 쪽은 DB 서버(t3.small, vCPU 2개) CPU가, 요청 쪽은 API 서버(t3.medium, vCPU 2개) CPU가 한계였다. 둘 다 CPU가 모자란 것이라 vCPU를 늘린다. 두 길은 Kafka로 나뉘어 있고 API는 발급 때 DB를 쓰지 않아서, 같이 키워도 효과를 길별로 나눠 볼 수 있다.

## 배치 INSERT

스케일 업에서 남은 목표는 DB 저장까지 60초(4)다. DB 서버 CPU는 21%가 남았는데 컨슈머는 초당 2,780건에서 멈췄고, 디스크는 초당 920번 × 0.97ms ≈ 0.89로 거의 쉬지 않고 쓰고 있었다. 컨슈머가 한 건마다 INSERT하고 커밋해서, 커밋할 때마다 binlog를 디스크에 쓰고 기다리는 줄이 꽉 찬 것으로 봤다. 그래서 한 건씩이 아니라 묶음으로 넣어 커밋 횟수를 줄인다.

```
전   메시지 1건 → INSERT 1번 → 커밋 1번 (binlog 기다림)       × 초당 2,780번
후   메시지 N건 → INSERT 문 1개 (VALUES N줄) → 커밋 1번        N건마다 한 번
```

- 리스너가 한 번에 꺼낸 메시지를 묶음째 받는다 (최대 2,000건). 한가할 때는 1건씩, Lag가 쌓이면 크게 묶인다
- JPA save 대신 JdbcTemplate.batchUpdate. ID가 자동 증가라 Hibernate는 묶어서 넣지 못해서 JDBC로 바꿨고, rewriteBatchedStatements로 묶음이 INSERT 문 하나가 된다
- INSERT IGNORE로, 장애 뒤 같은 메시지를 다시 받아도 유니크 제약에 걸린 줄은 건너뛴다
- 나머지는 스케일 업과 같음 (API · DB · k6 t3.xlarge, 컨슈머 스레드 30, flush 2, VU 5,000 17분, 재고 300만)

이번부터 재는 방법을 바꿨다.

- DB 저장까지 걸린 시간을 직접 잰다. 메시지가 Kafka에 들어간 시각부터 저장이 끝난 시각까지를 컨슈머가 기록한다. 지금까지는 Lag 최대 ÷ 처리량으로 어림했다
- 배치 리스너는 Spring의 리스너 지표가 묶음 단위로 세져서, 컨슈머 처리량 · 건당 시간은 저장한 메시지 수 지표로 본다. 배치 크기도 따로 본다
- MySQL 쿼리 수(Com_insert)는 이제 문장 수라서, 넣은 행 수(Innodb_rows_inserted)를 같이 본다
- fsync 패널에 binlog를 추가했다 (performance_schema 파일 지표의 sync 등). 커밋 때 기다리는 binlog를 처음으로 직접 본다

컨슈머가 초당 약 4,040건 이상 저장해서 DB 저장 60초를 지키는지, binlog fsync와 디스크 바쁜 비율이 얼마나 줄어드는지 본다. 저장이 빨라지면 컨슈머 서버 CPU(스케일 업 때 61%)가 다음 한계가 될 수 있다.

컨슈머가 처음부터 끝까지 발행을 따라가서 Lag가 거의 생기지 않았다. 직접 잰 DB 저장까지 걸린 시간은 p95 38ms, 가장 늦은 것도 0.2초였다.

예상과 달리 배치 크기는 평균 2건 안팎이었다. 줄이 쌓이지 않으니 한 번에 꺼낼 게 적었다. 그래서 커밋 수는 초당 약 2,780에서 2,500으로 비슷했는데, 커밋 한 번이 약 11ms에서 7ms 정도로 가벼워졌고 DB 서버는 일을 더 하면서도 CPU가 남았다(idle 21% → 40%). JPA로 저장할 때는 트랜잭션 시작 · INSERT · 커밋으로 DB와 여러 번 오갔는데, JDBC로 INSERT 문 하나(자동 커밋)를 보내면서 왕복이 줄어든 효과가 큰 것으로 보인다. 배치가 거의 1건이던 VU 1,000에서도 건당 시간이 7.8ms에서 5.4ms로 줄었다. 다만 저장 방식과 묶음을 같이 바꿔서 둘의 몫을 정확히 나누지는 못했다. 묶음은 줄이 쌓일 때 커져서 커밋 수를 줄이는 쪽으로 작동한다.

이번에 binlog를 직접 봤다. binlog sync가 초당 약 300번, 한 번에 약 3ms라 거의 쉬지 않고 돌았고(300 × 3ms ≈ 0.9), sync 한 번에 트랜잭션 8개 정도씩 묶어서 버텼다. 디스크 쓰기 1,040번 중 binlog sync는 300번 정도라, 지난번에 디스크 쓰기 대부분이 binlog일 거라고 본 건 틀렸다.

대신 인프라 서버 CPU가 최고 87%까지 올랐다. Redis가 쓴 건 코어 0.2개 정도라 대부분 Kafka다. 저장이 발행을 따라가면서 Kafka가 들어오는 것(초당 4,850건)과 나가는 것(초당 4,850건)을 같이 처리하고, 컨슈머가 작은 묶음으로 자주 가져가는 영향으로 보인다. 컨슈머 서버도 76%다.

## VU 10,000 진단

목표를 1초 10,000명으로 올렸다. 1초 5,000명일 때 CPU가 인프라 87%, 컨슈머 76%, API 67%, DB 57%, k6 54%였으니, 단순히 두 배로 보면 거의 모든 서버가 모자라다. 어디부터 막히는지 순서를 먼저 보려고, 측정 도구만 키우고 나머지는 그대로 둔 채 VU 10,000까지 올려 본다.

- 계단: 지금 계단의 두 배. 200 → 1,000(2분) → 2,000 → 3,000 → … → 8,000 → 10,000, 10,000에서 5분 (총 17분)
- 재고 600만 (이론상 최대 요청 약 560만)
- k6 서버 t3.xlarge → t3.2xlarge (vCPU 8개). 1초 5,000명에 54%였다
- 톰캣 최대 연결 8,192 → 20,000 (아래)
- 나머지는 배치 INSERT 때와 같음 (API · DB t3.xlarge, 인프라 · 컨슈머 t3.medium, 컨슈머 스레드 30, flush 2)

인프라(Kafka), 컨슈머, API, DB 중 무엇이 몇 VU에서 먼저 막히는지, 그때 응답 시간과 DB 저장까지 걸린 시간이 어떻게 되는지 본다.

### 톰캣 최대 연결

VU 10,000을 준비하면서 k6가 여는 연결 수를 계산해 보니 톰캣 기본 설정에 걸린다.

k6의 VU는 연결을 하나 열어 두고 계속 다시 쓴다(keep-alive). VU 10,000이면 API 서버에 연결이 동시에 10,000개 붙는다. 그런데 스프링 부트에 들어 있는 톰캣은 `server.tomcat.max-connections` 기본값이 8,192라서, 그 이상은 받지 않는다.

```
VU 10,000 ──연결 10,000개──▶ 톰캣 (최대 8,192)
                              ├─ 8,192개까지는 받음
                              └─ 나머지 약 1,800개는 OS 대기열(accept-count 100)에서 기다림
                                 → 대기열도 넘치면 연결이 안 되고, k6 타임아웃(60초)이 나면 실패로 잡힘
```

이대로 재면 찾으려는 병목(서버 CPU 등)이 아니라 설정값 때문에 실패가 생긴다. 그래서 최대 연결을 20,000으로 올렸다(VU 10,000의 두 배 정도로 여유를 둠).

```yaml
server:
  tomcat:
    max-connections: 20000
```

연결 수와 스레드 수는 다르다. 톰캣(NIO)은 연결을 많이 들고 있다가 요청이 들어온 연결만 스레드(200개)가 처리한다. k6 VU는 대부분 1초 쉬는 중이라, 연결은 10,000개여도 동시에 처리 중인 요청은 훨씬 적다. 그래서 스레드 수는 그대로 뒀다.

- 확인: 로컬에서 actuator의 `tomcat_connections_config_max_connections`가 20000으로 나오는 걸 봤다
- 대시보드 API 서버 줄에 "톰캣 연결 수" 패널(지금 연결 · 최대 설정)을 넣었다. 테스트 중에 연결이 10,000 가까이 차는지 본다
- 실제 서비스는 사용자마다 연결이 짧게 열고 닫히거나 로드밸런서가 연결을 모아 줘서 모양이 다르다. 그래도 큰 이벤트라면 서버 한 대의 최대 연결, OS의 열 수 있는 파일 수, 로드밸런서 설정을 같이 봐야 한다

인프라(Kafka)가 먼저 막힐 거라고 봤는데 아니었다. 발행 응답은 5ms 안팎이었고, 몰릴수록 프로듀서가 한 요청에 2건에서 14건으로 묶어 보내서 Kafka 요청 수는 오히려 초당 898에서 514로 줄었다. 그래도 인프라 서버 CPU는 86%라 목표(80%)는 넘었다.

저장 쪽은 끝까지 따라갔다. 컨슈머가 초당 약 7,430건을 저장했고 배치 크기가 1에서 3으로 커지며 버텼다. Lag는 최대 36, DB 저장까지는 p95 49ms였다.

## API 스케일 아웃

VU 10,000 진단에서 먼저 막힌 건 API 서버 한 대였다. CPU가 84%까지 올라 요청 한 건이 27ms로 길어졌고, 톰캣 스레드 200 ÷ 0.027초 ≈ 초당 7,400건에서 멈췄다. CPU가 거의 다 찼으니 스레드만 늘려서는 안 풀리고, CPU와 스레드를 같이 늘려야 한다. 서버 한 대를 더 키우는 대신 API를 두 대로 나누고 앞에 로드밸런서(nginx)를 둔다. API는 발급 상태를 Redis에 두고 서버에는 아무것도 들고 있지 않아서, 같은 API를 여러 대 띄우기만 하면 된다.

```
전   k6 ──▶ API 1대 (t3.xlarge) ──────────────────────────────┐
후   k6 ──▶ nginx (t3.medium) ──┬──▶ API ① (t3.xlarge) ──┬───┴──▶ Redis · Kafka
                                └──▶ API ② (t3.xlarge) ──┘
```

nginx 설정 (aws/split/lb)

- 두 API에 번갈아 보낸다 (round robin)
- `worker_connections 20000`: k6 연결 10,000개와 API로 가는 연결을 같이 들고 있어야 해서 기본값(1,024)으로는 모자란다. `worker_rlimit_nofile`과 컨테이너 `nofile`도 65,535로 올렸다
- API로 가는 연결은 keep-alive로 다시 쓴다 (`proxy_http_version 1.1`, `Connection ""`, upstream `keepalive 1024`). 안 그러면 요청마다 API와 연결을 새로 맺는다
- nginx 자체가 병목인지 보려고 stub_status + nginx-prometheus-exporter, LB 서버 CPU용 node-exporter를 같이 띄운다

대시보드는 API 패널을 서버별로 보이게 바꾸고(톰캣 스레드 · 연결 · CPU · 힙 · GC), "로드밸런서 (nginx)" 줄(LB 서버 CPU, nginx 초당 요청 · 연결, API 서버별 TPS)을 넣었다.

- k6는 API 대신 nginx로 보낸다
- 나머지는 VU 10,000 진단과 같음 (k6 t3.2xlarge, DB t3.xlarge, 인프라 · 컨슈머 t3.medium, 계단 17분, 재고 600만)
- 서버 8대, 약 $1.22/시간

API TPS가 VU 10,000에서 초당 9,500건 이상으로 오르는지, 두 API에 고르게 나뉘는지, nginx가 새 병목이 되지 않는지 본다. API가 다 받으면 Kafka에 들어오는 양도 초당 10,000건 가까이로 늘어서, 인프라(진단 때 86%)와 컨슈머 서버(76%)가 다음 한계가 될 수 있다.

그래도 VU 10,000 구간에서 초당 9,500건에는 조금 못 미쳤다(5분 평균 9,417). 거절된 요청은 없다. k6의 VU는 요청, 응답, 1초 쉬기를 되풀이해서 보내는 양이 10,000 ÷ (1초 + 응답 시간)이다. 9,500을 넘으려면 응답 평균이 50ms 안쪽이어야 하는데, 이 구간 응답 평균이 60ms 정도라 10,000 ÷ 1.06 ≈ 9,430에 머물렀다.

응답이 길어진 곳은 인프라 서버였다. API는 Kafka에 보내고 응답(ack)을 받을 때까지 기다린다. 인프라 서버 CPU가 VU 4,000 무렵부터 90%를 넘고 VU 10,000에서 95%까지 오르면서 Kafka 발행 응답이 2ms에서 8.5ms로 길어졌고, 서버 응답 평균도 4.6ms에서 22ms로 늘었다. 톰캣 스레드는 평균으로는 서버당 105개(초당 4,740 × 0.022초) 정도인데, Kafka 응답이 순간 느려질 때 한꺼번에 묶여 200까지 튀었다. 그때마다 줄이 생겨 서버가 잰 p95는 43ms인데 k6 p95는 133ms였다. API CPU(66%), GC(4% 안팎), Redis 명령 처리 시간(한 번에 2µs 안팎)은 여유가 있었다.

인프라 서버 CPU는 대시보드에 없어서 CloudWatch로 봤다. Redis 프로세스가 코어 0.35개 정도를 썼으니 나머지 대부분은 Kafka다. 다음에는 인프라 서버에도 node-exporter를 붙인다.

nginx는 연결 10,000개를 들고 초당 9,500건 가까이를 넘겼고, LB 서버 CPU는 58%였다. 그중 softirq(네트워크 패킷 처리)가 25% 정도로 가장 컸다. 요청 하나가 k6에서 nginx로, nginx에서 API로 두 번 오가기 때문이다. API의 톰캣 연결은 약 9,950개에서 서버당 수백 ~ 2,600개로 줄었다. nginx가 API로 가는 연결을 모아서 다시 쓰기 때문이다.

저장 쪽은 이번에도 따라갔다. 컨슈머가 초당 약 9,480건을 저장했고 배치 크기가 3.9까지 커졌다. DB 저장까지는 p95 58ms, 최대 0.56초였다. 다만 binlog sync가 초당 약 282번 × 3.2ms ≈ 0.9로 거의 쉬지 않고 돌고, 표 + 인덱스가 694MB로 버퍼 풀(256MB)보다 커서 VU 10,000에 들어갈 때 디스크 읽기가 잠깐 초당 10건까지 생겼다.

## 인프라 나누기 + Kafka 3대

API 스케일 아웃에서 막힌 건 인프라 서버였다. Redis, ZooKeeper, Kafka가 vCPU 2개짜리 서버 한 대에 있어서 CPU가 95%까지 올랐고, API는 Kafka 응답(ack)을 기다리기 때문에 Kafka가 느려진 만큼 요청이 길어졌다. Redis 프로세스는 코어 0.35개 정도라 대부분은 Kafka 몫이다.

Redis와 Kafka를 다른 서버로 나누면서, Kafka는 한 대가 아니라 세 대로 둔다. Kafka 서버가 하나뿐이면 그 서버가 죽을 때 발급 메시지를 받을 곳이 없어 요청 전체가 멈춘다. 한 대로 나눠 재고 다시 세 대로 늘리면 서버를 두 번 띄워야 해서 한 번에 바꿨다. 그래서 이번 결과에는 나눈 효과와 복제 3의 비용이 섞여 있다.

```
전   API ①② ──▶ 인프라 (t3.medium)   Redis · ZooKeeper · Kafka
후   API ①② ──┬──▶ Redis (t3.medium)
               └──▶ Kafka ① ② ③ (t3.medium 3대, 메시지마다 세 곳에 복사)
```

Kafka 설정 (aws/split/kafka)

- 서버 세 대에서 같은 파일을 띄우고 .env의 NODE_ID(1 · 2 · 3)와 자기 주소만 바꾼다
- ZooKeeper 없이 Kafka끼리 클러스터 정보를 관리한다(KRaft). 세 대가 브로커와 컨트롤러를 같이 맡고, 컨트롤러끼리 투표로 리더를 정한다. ZooKeeper를 계속 쓰면 ZooKeeper도 세 대가 있어야 한 대가 죽어도 버틴다
- `default.replication.factor 3`: 토픽을 만들 때 파티션마다 복사본을 세 브로커에 하나씩 둔다. 앱의 토픽 설정에서 `replicas(1)`을 빼고 Kafka 쪽 기본값을 따르게 했다. 로컬처럼 Kafka가 한 대면 1이 된다
- `min.insync.replicas 2`: 리더를 따라잡고 있는 복사본(ISR)이 2개보다 적으면 쓰기를 받지 않는다. 한 대가 죽으면 남은 두 곳에 써지니 계속 받고, 두 대가 죽으면 한 곳에만 써진 메시지를 잃을 수 있어 받지 않는다
- 컨슈머 오프셋 토픽도 복제 3
- 파티션 30개의 리더가 브로커마다 10개씩 나뉘어서, API가 보내는 메시지도 세 대로 나뉜다
- 프로듀서 설정은 그대로다. 지금 쓰는 Kafka 클라이언트(3.6)는 기본이 `acks=all`이라 리더가 ISR 전부에 복사될 때까지 기다린 뒤 응답한다. 지금까지는 브로커가 한 대라 리더만 쓰면 됐는데, 이제는 다른 두 브로커가 가져갈 때까지 기다린다
- 힙은 400MB 그대로

Redis 서버(aws/split/redis)에는 Redis, redis-exporter, node-exporter만 둔다.

모니터링

- 지난번 인프라 서버 CPU는 대시보드에 없어서 CloudWatch로 봤다. 이번에는 Redis · Kafka 서버 네 대에 node-exporter를 붙였다
- kafka-exporter는 모니터링 서버로 옮겨 브로커 세 대를 다 본다
- 대시보드에 "인프라 서버 (Redis · Kafka)" 줄을 넣었다: 서버별 CPU, Kafka 발행 응답(ack까지), 브로커 · 복제 상태(살아 있는 브로커, 가장 적은 ISR, 복제가 덜 된 파티션), 브로커별 리더 파티션 수

- 나머지는 API 스케일 아웃과 같음 (API 2대 · DB t3.xlarge, k6 t3.2xlarge, LB · 컨슈머 t3.medium, 계단 17분, 재고 600만)
- 서버 11대, 약 $1.38/시간

그런데 받아 낸 양은 늘지 않았다(5분 평균 9,345). Kafka 발행 응답이 8.5ms에서 16.6ms로 두 배가 됐기 때문이다. `acks=all`이라 리더가 받은 뒤 다른 두 브로커가 가져갈 때까지 기다리고, 그 브로커들도 70~80%로 바빴다. 부하가 작은 VU 1,000에서도 발행 응답은 2ms에서 4.6ms로 늘었다. Kafka 일은 세 대로 나뉜 게 아니라 세 배가 됐다. 지난번 Kafka 몫은 코어 1.5개 정도였는데, 이번에는 세 서버를 합쳐 4.4개 정도다. 메시지마다 세 브로커가 모두 받아 쓰고 브로커끼리 가져가는 요청이 생긴다. 프로듀서도 리더가 있는 브로커마다 따로 보내서 요청 하나에 담기는 메시지가 10.8건에서 5.7건으로 줄고 요청 수는 초당 976에서 1,664로 늘었다. VU 1,000에서 이미 Kafka 서버 CPU가 35~50%였다. Kafka 1번 서버만 다른 두 대보다 8%p 정도 더 바빴는데, 이유는 확인하지 못했다.

저장 쪽은 오히려 편해졌다. 컨슈머는 복사본 세 곳에 다 써진 메시지만 읽을 수 있어서 한 번에 더 많이 받았다(배치 3.9에서 5.3). 컨슈머 서버 CPU는 72%에서 61%, DB 서버는 61%에서 53%로 내려갔다. 대신 DB 저장까지 걸린 시간은 p95 58ms에서 87ms로 조금 늘었다.

### 대시보드로 원인 따라가기

받아 낸 양이 왜 안 늘었는지 요청이 지나가는 순서대로 패널을 따라가 봤다. 시각과 VU는 23:37~40 VU 1,000, 23:42 VU 4,000, 23:46 VU 8,000, 23:47~52 VU 10,000이다.

```
k6 ─▶ nginx ─▶ 톰캣 스레드 200 ─▶ API ─▶ Redis ─▶ Kafka (보내고 ack 기다림) ─▶ 202
       ③ 줄        ② 꽉 참          ④ 27ms              ⑤ ack 16.6ms, ⑥ Kafka CPU 70~80%
Kafka ─▶ 컨슈머 ─▶ MySQL   ⑦ 따라감
```

| 순서 | 패널 | 본 것 | 읽은 뜻 |
|---|---|---|---|
| ① | API 서버 "API TPS" | VU 10,000에서 202가 9.3~9.5K에서 평평, 200(매진 · 중복)과 실패는 0 근처 | 거절이 아니라 k6가 덜 보냄. k6는 응답을 받고 1초 쉬므로 응답이 길면 보내는 양이 준다 |
| ② | API 서버 "톰캣 스레드" | 23:42(VU 4,000)부터 두 서버 모두 200에 반복해서 닿음 | 평균은 서버당 130개쯤인데 순간 200이 다 차서 뒤 요청이 기다림 |
| ③ | 로드밸런서 "nginx 연결" | 처리 중(API 응답 대기)이 평소 수백, 23:45 · 23:48 · 23:50 무렵 2.5K~4.3K로 솟음 | ②와 같은 시각. 스레드가 꽉 찬 순간 요청이 nginx 앞에 쌓임. LB CPU는 60% 안팎이라 nginx 문제는 아님 |
| ④ | API 서버 "API 응답 시간", JVM "CPU 사용률" · "GC 멈춤 비율" | 서버 응답이 VU 1,000 7ms에서 VU 10,000 27ms로 오름. API CPU 60~65%, GC 2% 아래 | API가 계산하느라 바쁜 게 아니라 무언가를 기다림 |
| ⑤ | 인프라 서버 "Kafka 발행 응답" | VU 1,000 약 5ms, 23:41부터 오르기 시작해 VU 10,000 약 16.6ms (지난번 같은 지표 2ms → 8.5ms) | ④의 오르막과 모양이 같다. API 요청 27ms 중 약 19ms가 Kafka ack 기다리기 |
| ⑥ | 인프라 서버 "서버별 CPU" · "브로커 · 복제 상태" | Kafka CPU가 VU 1,000에서 이미 52 · 35 · 36%, VU 5,000부터 약 80 · 70 · 70%. 브로커 3, 가장 적은 ISR 3, 복제가 덜 된 파티션 0으로 끝까지 평평 | 복제가 밀린 게 아니라 세 곳에 정상적으로 복사하느라 드는 비용. `acks=all`이라 그만큼 ack가 늦다 |
| ⑦ | Kafka · 컨슈머 "발행 vs 처리" · "Consumer Lag", DB 서버 | 두 선이 끝까지 겹치고 Lag는 60~130짜리 바늘만. DB CPU 약 68%(node) 평평 | 저장 쪽은 원인이 아님. 23:46에 버퍼 풀 디스크 읽기가 잠깐 10까지 튄 건 다음 후보로 기억 |

정리하면 Kafka 3대 복제로 ack가 두 배 느려졌고, API 스레드가 ack를 기다리며 오래 붙잡혔고, Kafka가 순간 느려질 때 톰캣 200이 꽉 차 요청이 nginx 앞에 줄을 섰다. 그래서 k6 응답이 60ms 정도가 되어 10,000 ÷ 1.06 ≈ 9,430에서 막혔다. 지금 대시보드로는 ack 16.6ms가 브로커 안의 어느 구간(요청 대기, 리더 처리, 복제 기다림, 응답)에서 쓰였는지, Kafka 1번이 왜 더 바쁜지는 볼 수 없다.

복제 3은 안전을 얻는 대신 시간과 CPU를 낸다. 막힌 곳은 요청 쪽에서 API가 Kafka 응답을 기다리는 동안 톰캣 스레드를 붙잡고 있는 시간이다. 다음은 이 기다림을 다룬다.

## 톰캣 스레드 400 + Kafka 브로커 지표

인프라 나누기 + Kafka 3대에서 톰캣 스레드가 순간 200에 닿아 요청이 줄을 섰다. 그런데 API CPU는 60~65%로 여유가 있었다. 스레드가 일을 하느라 모자란 게 아니라 Kafka ack를 기다리며 놀고 있었다. CPU에 여유가 있으니 스레드를 400으로 늘려 본다.

```yaml
server:
  tomcat:
    threads:
      max: 400
```

- 기대: Kafka가 순간 느려져도 400 안에서 받아 줘서 nginx 앞에 줄이 안 생긴다. k6 응답이 서버 응답(27ms 안팎)에 가까워지면 10,000 ÷ 1.03 ≈ 9,700으로 목표 3을 넘을 수 있다
- 안 바뀌는 것: Kafka ack 시간과 Kafka CPU(목표 6)
- 대가: 스레드가 많아지면 API CPU가 조금 오르고, 동시에 처리하는 요청의 상한이 200에서 400으로 느슨해진다. Kafka가 멈추면 기다리며 쌓이는 요청도 그만큼 많아진다

ack가 늦은 근본 원인은 Kafka 쪽이다. 그런데 지금은 API가 잰 "보내고 ack까지" 시간만 있어서 브로커 안 어디서 늦는지 모른다. Kafka 브로커는 요청 하나를 받아 응답할 때까지를 구간별로 재고 있어서, 이걸 수집한다.

```
API ─produce─▶ 리더 브로커
                 요청 대기     I/O 스레드가 비기를 기다림
                 리더 처리     자기 로그에 씀
                 복제 기다림   팔로워 둘이 가져갈 때까지 (acks=all)
                 응답 대기 · 전송
             ◀─ack─
```

- Kafka에 JMX exporter(javaagent)를 붙여 브로커 지표를 Prometheus로 내보낸다. 에이전트 jar는 Kafka 서버에서 compose가 Maven Central에서 받아 쓴다
- 수집하는 것: 요청 종류(발행, 팔로워 복사, 컨슈머 가져오기, 오프셋 커밋)별 초당 수와 구간별 처리 시간(중앙값, p95), I/O · 네트워크 스레드가 노는 비율, 어느 브로커가 컨트롤러 · 그룹 코디네이터인지
- 대시보드에 "Kafka 브로커" 줄을 넣었다
- 에이전트가 지표를 모으느라 Kafka CPU를 조금 더 쓴다
- 에이전트를 `KAFKA_OPTS`로 붙여서, 컨테이너 안에서 `kafka-topics` 같은 도구를 그대로 실행하면 그 도구도 에이전트를 같은 포트(7071)로 띄우려다 실패한다. 도구를 쓸 때는 `docker exec -e KAFKA_OPTS= …`로 비우고 실행한다
- KRaft에서 한 서버가 브로커와 컨트롤러를 같이 맡아서, I/O 스레드가 노는 비율은 두 스레드 묶음의 합으로 나온다(최대 2)

EC2는 한 번 켜서 두 번 잰다. 1회차는 톰캣 400만 바꾼 결과와 ack가 어디서 쓰이는지를 본다. 서버를 켠 채로 1회차를 읽고 Kafka 쪽 손잡이를 하나 골라(오프셋 커밋 줄이기, 프로듀서 `linger.ms`, `num.replica.fetchers` 중) 2회차에 그것만 바꿔 다시 잰다.

- 나머지는 인프라 나누기 + Kafka 3대와 같음 (11대, 약 $1.38/시간, 계단 17분, 재고 600만)
