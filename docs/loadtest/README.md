# 부하 테스트 결과 (열린 모델)

## 목표

초당 10,000건의 쿠폰 발급 요청을 5분 동안 받아 내는 구조를, 서버를 가장 싸게 써서 만든다. 중간 단계부터는 서버 한 대가 죽어도 버티게 한다.

한 번에 10,000으로 가지 않고 초당 500건부터 올린다. 단계마다 아래 기준을 넘으면 다음 단계로 가고, 못 넘으면 지표로 막힌 곳을 찾아 가장 싸게 고친 뒤 다시 잰다.

```
초당 500 → 1,000 → 2,000 → 3,000 → 5,000 → 7,000 → 10,000
```

| # | 항목 | 기준 |
|---|---|---|
| 1 | 응답 | p95 500ms 이하 (p90도 함께 적음) |
| 2 | 실패 | 0 |
| 3 | 받아 낸 양 | 그 단계 목표의 99% 이상 (목표 구간 5분 평균) |
| 4 | DB 저장까지 | 60초 이내 |
| 5 | 정합성 | k6 발급(202) 수 = Redis 셋 = Redis 순번 = DB |
| 6 | 서버 여유 | 가장 바쁜 서버 CPU 80% 이하. 고가용성 단계부터는 한 대가 죽었을 때 남은 서버로 기준을 지키는지 |
| 7 | 측정 신뢰 | k6 서버 CPU 80% 이하 |
| 8 | 비용 | 서비스 서버(k6 · 모니터링 제외) EC2 시간당 비용을 단계마다 적고, 같은 단계를 넘는 구성이면 더 싼 쪽을 고른다 |

### 부하를 거는 방식

k6 열린 모델(`ramping-arrival-rate`)로 정해진 양을 응답과 상관없이 보낸다. 실제 사용자는 서버가 느려졌다고 덜 누르지 않는다. VU가 응답을 받고 1초 쉬는 닫힌 모델은 응답이 길어지면 보내는 양이 저절로 줄어서, 서버가 못 받는 건지 덜 보낸 건지 구분하기 어렵다.

```
k6 run -e RATE=<단계 목표> -e SHAPE=step -e BASE=… -e QUANTITY=… k6/coupon-issue.js
```

- `SHAPE=step`: 목표의 2% → 10%(2분) → 20% → 30% → … → 80% → 100%(5분), 17분. 어느 양에서 무엇이 먼저 꺾이는지 보려고 계단으로 올린다
- k6가 VU가 모자라 못 보낸 요청은 `dropped_iterations`로 따로 나온다
- 응답 종류를 따로 센다: `issued`(202 발급), `rejected`(200 매진 · 중복)

## 출발 구성

처음부터 역할별로 서버를 나누고, 가장 작은 크기로 시작한다.

```
k6 ─▶ API ─┬─▶ Redis
           ├─▶ MySQL (발급 요청마다 쿠폰 수량 조회)
           └─▶ Kafka (1대) ─▶ 컨슈머 ─▶ MySQL
```

| 서버 | 크기 |
|---|---|
| API, Redis, Kafka, 컨슈머, DB | 각각 t3.small (vCPU 2, 메모리 2GB) |
| 모니터링 | t3.small |
| k6 | 단계에 맞춰 (측정 도구가 먼저 막히지 않게) |

서비스 서버 5대, 시간당 약 $0.13.

앱은 맨 처음 코드에서 시작한다. 튜닝을 하나씩 다시 하면서 효과를 잰다.

- 발급 요청마다 쿠폰 수량을 DB에서 조회하고, Redis로 중복(SADD)과 순번(INCR)을 판정한 뒤 Kafka에 발행하고 ack를 기다려 202
- OSIV, 톰캣 스레드, DB 커넥션 풀, MySQL 설정은 모두 기본값
- 토픽 파티션 3, 컨슈머 스레드 3, 한 건씩 JPA로 저장하고 매번 커밋
- Kafka는 한 대 (KRaft, 복제 1). 나중에 `.env`의 `KAFKA_VOTERS` · `REPLICATION` · `MIN_INSYNC`로 세 대로 늘린다

측정 도구는 튜닝이 아니라서 처음부터 다 둔다.

- Grafana 대시보드 (API · Kafka · 컨슈머 · Redis · MySQL · 서버 CPU, Kafka 브로커 지표)
- Kafka 브로커 지표 (JMX exporter)
- 컨슈머의 "발행부터 DB 저장까지 걸린 시간"과 저장 건수
