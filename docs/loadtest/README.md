# 부하 테스트 결과

## 환경

- AWS 서울 리전, t3.medium 2대 (같은 서브넷)
- 앱 서버 1대에 api, consumer, MySQL, Redis, Kafka, Prometheus, Grafana를 전부 컨테이너로 올림
- k6 서버에서 앱 서버 사설 IP로 부하를 줌
- Rate Limiter 없음

발급 흐름은 Redis로 중복이랑 순번을 판정하고, Kafka에 발행해서 ack를 받으면 202를 준다. DB 저장은 컨슈머가 따로 한다.

통과 기준은 k6 threshold 그대로 성공 응답 99% 이상, p95 10초 이하.

## VU 500, VU 1,000 (OSIV 켜진 상태)

| | VU 500 (1-1) | VU 1,000 (1-2) |
|---|---|---|
| 결과 | 통과 | 통과. OSIV를 끄고 얼마나 나아지는지 확인 필요 |
| 부하 | 0 → 100 → 400 → 500, 12분 | 0 → 100 → 400 → 700 → 1,000, 15분 |
| 재고 | 10만 | 60만 |
| 요청 수 / 실패 | 248,733 / 0 | 421,201 / 0 |
| p95 (k6) | 55ms | 1.03s |
| API TPS | 평균 345, 발급 구간 최대 약 415 | 평균 465, 최대 709 (650~680에서 더 안 올라감) |
| 컨슈머 TPS | 최대 258 (250 근처에서 평평) | 최대 254, VU 700 넘어서는 약 210 |
| Lag 최대 | 28K, 매진 후 2분쯤 지나 0 | 247K, 부하 끝나고 14분쯤 지나 0 |
| 앱 서버 CPU | 최고 76% | 96% |
| 특징 | 컨슈머가 초당 250건 정도에서 막혀서 Lag가 쌓임. 매진 직전에 API DB 커넥션 대기가 잠깐 190 가까이 튐 | 톰캣 스레드 200개가 다 참. API DB 커넥션 10개를 다 쓰고 190개 정도가 대기. CPU도 거의 다 씀 |
| 발급 수량 | 100,000장 (DB, Redis 같음) | 421,201장 (DB, Redis 같음) |

- VU 500은 재고 10만이 중간에 다 나가서 500 VU 구간은 매진 응답만 받았다. API 최대 496/s도 매진 응답 기준이라 표에는 발급 구간 값을 적었다.
- VU 1,000은 15분 동안 계속 발급되게 재고를 60만으로 잡았다.

## API DB 커넥션 대기

VU 1,000에서 VU 700을 넘어가면서 이렇게 됐다.

| 항목 | 값 |
|---|---|
| 톰캣 스레드 | 200 / 200 |
| API DB 커넥션 | 10 / 10 사용, 약 190 대기 |
| MySQL 실행 중 쿼리 | 4~7개 |

DB는 별로 바쁘지 않은데 커넥션이 모자랐다. 커넥션 10개로 초당 670건 정도를 처리했으니 요청 하나가 커넥션을 15ms쯤 잡고 있었던 셈이다. 쿠폰 조회 한 번은 1ms도 안 걸린다.

원인은 OSIV(open-in-view)로 봤다. 기본값이 켜져 있어서 쿠폰 조회 때 가져간 커넥션을 요청이 끝날 때까지 들고 있는다. 그 사이에 Redis 호출이랑 Kafka ack 기다리는 시간도 다 들어간다.

```
OSIV 켜짐   조회 ── 커넥션 ═════════════════════════ 요청 끝날 때 반납
                     (Redis, Kafka ack 기다리는 동안에도 들고 있음)
OSIV 꺼짐   조회 ── 커넥션 ═ 바로 반납
```

VU 500 때도 같은 상황이었다. 매진 직전에 발급이 초당 415건 정도일 때 커넥션 대기가 잠깐 190 가까이 올라갔다.
그런데 매진 뒤에는 매진 응답을 초당 490건 정도로 더 많이 처리했는데도 대기가 없었다. 매진 응답은 Kafka를 안 거치니까, Kafka ack를 기다리는 동안 커넥션을 들고 있는 게 큰 것 같다.
